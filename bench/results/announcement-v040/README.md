# v0.4.0 bounded build-reuse measurement

This is one small build workload, not a general Honk speed ranking. It measures
the released v0.4.0 executable against retained v0.2.0 and keeps the cost of
populating a reuse slot and the unsupported-input fallback. The documentation
update changes none of the measured runtime, compiler, dependency or harness files.

## Inputs and method

- Candidate: `f9f35e20e4407df56b2ad45310266c9238403144` (v0.4.0); baseline:
  `855fb0552aefd5f0c033826af64f3bdd09ae6482` (v0.2.0). Both Honk binaries were
  built previously with `make build` (default optimized Goose/C build); no new
  Honk/compiler build was performed for this run. Their exact executed hashes
  are in [verification.json](verification.json). Rebuilding may produce different bytes.
- Goose: `eadca409f68210893f366e60d0c2f0dc29a339be`, executable SHA-256
  `7ffde13da95fbbdaa15b27419494fc9b71f2c91c0b4c4d732f51815e928a4b56`.
  The clean compiler checkout, standard-library and runtime Git trees were checked.
  Post-run loaded-library hashes and libcurl 8.23.0/libsodium 1.0.22 versions are
  recorded; they do not attest every indirect C-toolchain input before/after.
- Intel Core Ultra 7 258V, Linux 7.2.11 x86-64, glibc 2.44, GCC 16.2.1
  (20260810); fixture files on `/tmp` tmpfs; controller and children pinned to CPU0.
  Other coordinated heavy jobs were held, but ordinary host activity remained.
  This is not an isolated-host measurement.
- Unchanged [`bench/reuse.py`](../../reuse.py), SHA-256
  `d7d538fee3cd3cc7b51d7c04db8b1d63284a54937c346e8e7757e3d02b74111b`.
  Two identical small SemVer CLI projects, one with an unused native sidecar
  that forces conservative fallback. SemVer source/license match full pin
  `2311ae69a7edacb545f284b02e345be07dd2fb05`; all fixture/lock hashes are retained.
- Selected application **debug** builds, nine shuffled rounds of four modes per
  fixture: 72 timed builds, seed 20261105. Every build is followed by a checked
  executable run printing `match`. One build/run per fixture/mode warms up first;
  three extra warm-cache preparations are retained separately from timed samples.
  Compiler/runtime and OS caches are warm. "Cold" clears only the Honk reuse slot.
- Wall time includes process launch, Honk work and compiler work when invoked.
  CPU time is child user+system time. Application checks, setup and warmups are
  outside the timed samples. A backend-log sentinel and independent Python
  digest verify the eligible hit; fallback still invokes the compiler.

The single invocation ran 2026-11-05 21:26:25.373797–21:27:17.069724 UTC
(51.696 seconds including setup, warmups, samples and cleanup), exited 0, and
left no controller group or adopted children. There was no retry or second series.

## Results

Values are **median [minimum, maximum] milliseconds**, nine samples per row.
Full ranges and all slower observations are retained; no trimming or timing threshold.

| Fixture | Build mode | Wall ms | CPU ms |
| --- | --- | ---: | ---: |
| Unused-sidecar fallback | v0.2.0 ordinary | 491.303 [450.970, 502.748] | 470.300 [446.374, 479.751] |
| Unused-sidecar fallback | v0.4.0 empty reuse slot | 494.613 [445.331, 518.816] | 474.069 [440.612, 478.691] |
| Unused-sidecar fallback | v0.4.0 ordinary | 480.657 [444.691, 498.068] | 472.242 [440.329, 475.195] |
| Unused-sidecar fallback | v0.4.0 warm reuse request | 482.593 [442.354, 497.340] | 466.422 [437.858, 473.350] |
| Source only | v0.2.0 ordinary | 490.874 [446.884, 499.051] | 468.149 [442.365, 478.969] |
| Source only | v0.4.0 empty reuse slot | 1514.833 [1459.225, 1604.101] | 1494.300 [1447.523, 1530.276] |
| Source only | v0.4.0 ordinary | 487.987 [454.157, 578.802] | 468.095 [449.344, 553.613] |
| Source only | v0.4.0 warm reuse request | 72.580 [68.008, 73.728] | 69.521 [66.928, 71.131] |

The eligible warm request skips the backend for this fixture. Populating its
slot is substantially slower than an ordinary build: population builds a
standalone executable rather than consuming the compiler's mutable runtime
object. Equal cold code generation or equal generated bytes are not asserted.
Ordinary and fallback ranges overlap. A warm request on the sidecar fixture
falls back to normal compilation; it is not a cache hit. These are whole
implementations, so differences from v0.2.0 do not isolate one optimization.

No allocation, RSS, long-running stability, general dependency workload, Cargo
comparison or universal speedup is measured. Indirect system toolchain files
are not exhaustively fingerprinted; the [reuse contract](../../../docs/INCREMENTAL-BUILDS.md)
requires them to remain unchanged.

## Reproduce the protocol

Install the [documented build dependencies](../../../README.md). With a trusted
compiler at the exact `GOOSE_REVISION`, build each source revision in a separate
clean clone. Use absolute paths and a fresh output file:

```sh
git clone --branch v0.4.0 --depth 1 https://github.com/carabistouflette/honk.git honk-v040
git clone --branch v0.2.0 --depth 1 https://github.com/carabistouflette/honk.git honk-v020
make -C honk-v040 GOOSE=/absolute/pinned/goose build
make -C honk-v020 GOOSE=/absolute/pinned/goose build
mkdir -p honk-v040/.build
taskset -c 0 python3 honk-v040/bench/reuse.py \
  --honk "$PWD/honk-v040/.build/honk" \
  --baseline "$PWD/honk-v020/.build/honk" \
  --goose /absolute/pinned/goose --rounds 9 \
  --output "$PWD/honk-v040/.build/reuse-new.json"
```

Ensure CPU0 is available, preserve the clean source state, and keep `GOOSE_CC`
unset so both builds use the default C compiler. Supply the recorded binaries
to replay those exact executed images; source rebuilds reproduce the protocol,
not necessarily the image hashes or timings. Record the new machine/tool/input
identities and retain setup, warmups and all samples. On a shared host, arrange
a finite measurement window first. A new run must not replace this raw record.

Recompute the summary without running Honk or the benchmark:

```sh
python3 - <<'PY'
import collections, json, statistics
from pathlib import Path
data = json.loads(Path("bench/results/announcement-v040/samples.json").read_text())
groups = collections.defaultdict(list)
for sample in data["samples"]:
    groups[sample["fixture"], sample["mode"]].append(sample)
for key, samples in sorted(groups.items()):
    print(key, len(samples))
    for field in ("wall_ms", "cpu_ms"):
        values = [sample[field] for sample in samples]
        print(field, statistics.median(values), min(values), max(values))
PY
```
